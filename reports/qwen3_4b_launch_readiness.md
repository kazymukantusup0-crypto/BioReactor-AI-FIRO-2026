# Qwen3 4B — проверка возможности безопасного запуска

Дата измерений: 2026-11-11, Asia/Qyzylorda. **Статус BLOCKED: загрузка и генерация не запускались.** Qwen3 8B остаётся установленной; production-конфигурация и настройки Ollama не изменены.

## Профиль и допуск

Подготовлен отдельный [профиль](../evaluations/qwen3_4b_profile_20261111.json): `qwen3:4b-q4_K_M`, `num_ctx=4096`, `num_batch=32`, `num_gpu=-1`, `keep_alive=0`, максимум один запрос от экспериментального клиента. Это проект параметров, а не проверенный runtime. Установленный Ollama в момент проверки — **0.40.16**, не 0.40.15 из исходных данных; происхождение обновления не исследовалось.

В исходном коде [Ollama 0.40.16](https://github.com/ollama/ollama/blob/v0.40.16/llm/llama_server.go) `num_gpu=-1` оставляет выбор размещения runner; полный GPU offload не гарантирован. Свободная VRAM около 7.3 GiB больше размера файла модели, но KV-cache, рабочие буферы, резерв GPU и копии/отображения в RAM не измерены. Поэтому размер файла не доказывает достаточность RAM или VRAM.

В окружении работающего сервера PID 15836 переменная `OLLAMA_NUM_PARALLEL` отсутствует. [Документация Ollama](https://docs.ollama.com/faq) описывает эту серверную настройку и её влияние на память; фактическое число слотов в текущем процессе не измерено. Клиентская последовательная отправка запросов не исключает сторонних запросов. Необходим отдельный контролируемый сервер либо доказанное отсутствие конкурирующих запросов и подтверждённая конфигурация слотов без изменения production.

Согласно [API Ollama](https://docs.ollama.com/api/chat), `keep_alive=0` запрашивает выгрузку по завершении запроса. Поэтому отдельная предварительная загрузка с тем же `keep_alive=0` не обеспечивает сохранение модели между загрузочным запросом и генерацией; для исходного профиля загрузку и генерацию следует измерять как стадии одного запроса и затем отдельно подтвердить выгрузку через `/api/ps` и телеметрию.

Допуск для 4B не копирует численный cold-start gate 8B. Условия: три свежих замера, работающая телеметрия и API, отсутствие конкурирующего inference; физическая RAM и commit headroom должны покрывать проверенную верхнюю границу пикового потребления **именно этого профиля**, обоснованный резерв ОС и запас на задержку фактической остановки; VRAM должна покрывать размещение с резервом; отсутствие thermal slowdown и соблюдение действующего локального ограничения GPU gate. Пиковые значения 4B, резерв и задержка остановки загрузки неизвестны. Поэтому численный безопасный порог пока не установлен. Прежний локальный runtime floor 6246.4 MiB для других сценариев не объявляется пределом безопасности 4B; текущие измерения ниже него подчёркивают отсутствие запаса относительно ранее действовавшей защиты.

## Выполнение и интеграция

| Проверка | Результат |
|---|---|
| Загрузка, пик RAM/commit/VRAM, размещение | **NOT RUN** — допуск BLOCKED |
| Короткий запрос, скорость, качество и tool calling | **NOT RUN** |
| Выгрузка и восстановление ресурсов | **NOT RUN** |
| Реальная остановка загрузки/генерации после закрытия HTTP | **NOT RUN**; закрытие соединения не считается доказательством остановки |
| Переключение production | **NOT DONE** |

Текущий `JSONProvider` допускает выбор через `OLLAMA_MODEL` в отдельном процессе; `BIOREACTOR_LLM_CONTEXT=4096` может явно задать контекст такого процесса. Это не меняет бизнес-логику. Однако существующий production provider не передаёт требуемые `num_batch=32` и `keep_alive=0` как полный изолированный профиль, а серверная параллельность задаётся отдельно. Поэтому переключение подготовлено только как конфигурационный вариант для будущей QA-проверки, не как утверждение о готовой интеграции. Текущий `data/config/llm_selection.json` по-прежнему выбирает `qwen3:8b`; откат QA-процесса — завершить только свой QA-процесс и не задавать `OLLAMA_MODEL`/override при новом запуске. Перезапускать пользовательский Dashboard и сервер Ollama не требуется для этой диагностики.

## Следующие условия

Нужно получить воспроизводимую верхнюю границу пика RAM/commit/VRAM и задержки остановки для этого профиля в условиях, выдерживающих полный пик без зависимости от мгновенной отмены; измерить наличие конкурирующих запросов и работу единственного слота. Практический вариант — использовать машину или конфигурацию с большим реально доступным запасом памяти, выполнить контролируемую серию с непрерывным мониторингом, а затем повторить трёхточечный допуск непосредственно перед тестом на ноутбуке. При изменении свободной RAM исходные пороги не считать автоматически безопасными. При потере телеметрии, thermal slowdown, CUDA crash или достижении заранее обоснованного предела — остановить только собственный запрос и подтвердить прекращение нагрузки отдельно.

Последующий пассивный снимок групп процессов показал приблизительно 2786 MiB суммарного working set у 13 `Code.exe`, 2604 MiB у 21 `comet.exe`, 421 MiB у 5 процессов NVIDIA Overlay и 283 MiB у WhatsApp. Значения нескольких процессов могут включать общие страницы и не равны гарантированно освобождаемой памяти. Для увеличения запаса пользователь может сохранить работу и вручную закрыть ненужные окна браузера или редактора; процессы автоматически не завершались. Одного освобождения RAM недостаточно без оценки пика профиля и проверенного сценария остановки.

После успешного первого запуска и подтверждённой выгрузки проводить последовательно русскоязычное объяснение BMP, недостающие данные, единицы, многоходовый диалог и tool calling через проверяемые инструменты BioReactor AI. Один самостоятельный ответ модели не подтверждает научное качество агента. **BioReactor AI остаётся NOT READY.**
