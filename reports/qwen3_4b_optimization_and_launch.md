# Qwen3 4B: оптимизация и подготовка запуска

Дата: 2026-11-11, Asia/Qyzylorda. **Допуск BLOCKED, live Qwen NOT RUN; проект NOT READY.** Пользователь подтвердил закрытие Comet и сообщил свои замеры 7036.5 / 6835.2 / 6952.5 MiB; приведённая ниже новая серия измерена отдельно.

## Профиль и сохранение конфигурации

Подготовлен `evaluations/qwen3_4b_compact_profile_20261111.json`: модель `qwen3:4b-q4_K_M`, `num_ctx=2048`, `num_batch=16`, `num_gpu=-1` (автовыбор), `keep_alive=0`, один запрос клиента; планируемый отдельный Ollama на 127.0.0.1:11479 с `OLLAMA_NUM_PARALLEL=1` только в его окружении. Автовыбор не гарантирует полного GPU offload. Экспериментальный профиль не переключён в production: сохранённые настройки `data/config/llm_selection.json` продолжают выбирать `qwen3:8b`, fallback `qwen2.5:1.5b`, контекст 2048. При отдельном запуске QA выбор `OLLAMA_MODEL` и контекста передаётся через окружение процесса; текущий production provider не реализует все настройки compact profile и не изменялся. Откат — завершить только QA-процесс и убрать его локальные переменные; существующая конфигурация 8B не переписывалась.

`python -X utf8 evaluations/qwen3_4b_compact_plan.py` проверяет профиль и Unicode и формирует preview запроса; запуска модели и telemetry в этом скрипте нет. Состояние `BLOCKED` формируется при отсутствии границ ресурсов и подтверждённой изоляции runner. Этот файл — проверка плана, не готовый безопасный live runner. Существующий монитор `evaluations/qwen_offload_ab_harness.py` собирает RAM, commit, GPU, thermal slowdown и Ollama, но его live-режим жёстко настроен на 8B и действующий 8B gate; для 4B его запускать нельзя. Отдельный безопасный runtime контроллер 4B ещё требуется.

## RAM и архитектура

В `src/agent/tools.py` `predict_tool` раньше загружал bundle Stage 1.5 для domain detector и повторно загружал тот же bundle при `predict_bmp`. Теперь одна загрузка передаётся во внутренний параметр `predict_bmp` и используется для обоих действий. Для legacy Stage 1 отдельный Stage 1.5 detector всё ещё нужен, а его bundle и выбранная Stage 1 модель остаются разными. Тест `test_stage1_5_reuses_the_detector_bundle_for_prediction` подтверждает **1 вызов joblib.load вместо 2 по прежнему коду**; проверки сравнивают предсказание и проверку применимости двух сохранённых bundle. Размер сэкономленной RAM и пик процесса **не измерены**, нельзя выводить MiB из числа загрузок. Нет постоянного кеширования загруженного bundle и зависимостей от истории других пользователей.

Диалоговая история ограничена последними восемью ходами, provider формирует контекст из четырёх или шести последних ходов, но наличие лимита токенов конкретного запроса и качество при 2048 токенах ещё не проверены. Научные JSON профили уже используют bounded `lru_cache(maxsize=8)` и `deepcopy` для изоляции изменений; cache не уменьшался без проверки корректности. `JSONProvider` создаётся для запроса, но является лёгким объектом и не загружает веса Qwen в Python. Dashboard `models_status` кэширует результаты проверки bundle, но первый вызов загружает артефакты; изменять семантику проверки совместимости только ради предположительной экономии не стали. Планировщик рынка можно отключить для изолированного QA через `scheduler_enabled=False`; production не менялся.

Пассивный список видимых Python-процессов на момент проверки показал только собственный короткий процесс диагностики; это не доказывает отсутствие всех процессов при недостатке прав. Пользовательские процессы не закрывались. Реальная экономия общей RAM от остановки Comet в этом подэтапе не приписывается изменению кода.

## Свежий 4B preflight

После подтверждения пользователя получены три снимка с промежутком 10 секунд, сохранены в `reports/qwen3_4b_compact_preflight_20261111.json`:

|---|---:|---:|---:|---:|
| 15:34:44 | 6940.3 | 21905.3 | 61 / 9% | 576 / 8192 |
| 15:34:54 | 7013.1 | 22044.3 | 61 / 16% | 576 / 8192 |
| 15:35:04 | 6985.3 | 21994.1 | 61 / 10% | 576 / 8192 |

HW/SW thermal slowdown не активны; API Ollama **0.40.16**, `/api/ps` пуст во всех трёх снимках. В списке GPU-процессов несколько PID имеют `Insufficient Permissions`, поэтому полностью исключить стороннюю GPU-задачу нельзя. Установлены qwen3:4b-q4_K_M, qwen3:8b и qwen2.5:1.5b; модель 8B не изменялась.

**Конкретная причина BLOCKED:** для Qwen3 4B на ctx 2048 / batch 16 ещё не установлены верхняя граница peak commit, вклад mapped files и GPU driver в физическую память, резерв VRAM/ОС и время фактической остановки при загрузке; кроме того, runner с загруженной моделью ещё не проверен на принадлежность ограниченной job и освобождение GPU. Пройденные ранее тесты Job Object охватывали синтетические процессы и Ollama без модели, не 4B runner. Квота commit не является лимитом RAM или VRAM. 8B gate не переносился как 4B допуск, не ослаблялся и не обходился. Доступная RAM увеличилась, но это не доказывает безопасности первого cold start.

Минимальное следующее действие: подготовить отдельный QA server с изолированным model store и контроллером Job Object, который подтверждает принадлежность runner и мониторит физическую RAM, commit, VRAM, GPU и реальное завершение. Для первого запуска нужны обоснованные ограничения на оставшиеся неподконтрольные job ресурсы и резерв ОС; practically их следует сначала определить на сопоставимом GPU/backend с большим подтверждённым запасом RAM. Если таких данных или площадки нет, следующий запуск остаётся BLOCKED. После получения доказательств заново снять три последовательных замера непосредственно перед одним запросом; при потере телеметрии, thermal slowdown или нарушении доказанных пределов остановить только QA job и проверить фактическое прекращение GPU работы. `keep_alive=0` не позволяет считать модель загруженной после завершения предварительного запроса; загрузку и ограниченную генерацию нужно наблюдать в рамках одного контролируемого запроса.
