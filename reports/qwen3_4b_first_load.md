# Qwen3 4B: изоляция первого запуска

Дата: 2026-11-11, Asia/Qyzylorda. **Статус первого запуска: BLOCKED / NOT RUN.** Успешная проверка Job Object и пустого сервера Ollama не подтверждает безопасную загрузку Qwen или остановку CUDA runner.

## Окружение и подтверждённые измерения

Проверено: `sys.getwindowsversion()` — `10.0 build 26200`, реестр — `DisplayVersion=25H2`, `CurrentBuildNumber=26200`, `UBR=9711`, `ProductName=Windows 10 Pro`. Это противоречивое название в реестре: [Microsoft относит build 26200.9711 к Windows 11 25H2](https://learn.microsoft.com/en-us/windows/release-health/windows11-release-information). Поэтому тест относится к обнаруженной сборке Windows 11; на отдельной системе Windows 10 он не выполнялся. CIM Win32_OperatingSystem вернул Access denied.

Драйвер NVIDIA 581.80, RTX 3070 Laptop 8192 MiB; Ollama API/CLI 0.40.16. Одно измерение после проверок в 15:18:44 +05: доступная RAM 4395.5 MiB; commit headroom 19325.0 MiB; GPU 59 °C, utilization 39%, VRAM 750/8192 MiB; hardware/software thermal slowdown не активны, API отвечает, `/api/ps` пуст. Это одиночное наблюдение, не трёхточечный допуск и не замер пика модели. GPU utilization показывает фоновую нагрузку, её источник этим снимком не установлен.

## Подтверждённая изоляция

[Microsoft: Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) поддерживают группы процессов, наследование для обычного `CreateProcess` и иерархию вложенных jobs начиная с Windows 8. `Win32_Process.Create`, breakaway и внешние службы требуют отдельной проверки. [ProcessMemoryLimit и JobMemoryLimit](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information) ограничивают commit, а не физический working set и не VRAM. Эти ограничения не доказывают верхнюю границу воздействия mapped files, драйвера, кэша, GPU и системных компонентов.

Тестовый bootstrap сначала ожидает разрешение родителя через pipe, запускает потомков только после помещения в job. Для произвольного исполняемого файла, способного немедленно создать детей, потребуется атомарная привязка при создании или `CREATE_SUSPENDED` → назначение job → `ResumeThread`; этот вариант для `ollama.exe` ещё не реализован. Пустой тестовый сервер не запускает runner, поэтому принадлежность реального runner job, отсутствие breakaway и время прекращения CUDA работы пока не подтверждены. Тест завершил только собственные процессы, основной сервер и пользовательские приложения не затрагивались.

## Профиль первого эксперимента

Профиль `evaluations/qwen3_4b_profile_20261111.json`: `qwen3:4b-q4_K_M`, `num_ctx=4096`, `num_batch=32`, `num_gpu=-1` (автовыбор, не гарантия полного GPU), `keep_alive=0`, один одновременный запрос. QA-сервер — отдельный loopback-порт и job с per-process и aggregate commit caps; монитор должен фиксировать RAM, commit, GPU temperature, HW/SW slowdown, utilization, VRAM, PID и `/api/ps`, а аварийная остановка — завершать только собственную job и проверять, что runner/GPU нагрузка прекратились. Замена данных модели отдельной копией в изолированном каталоге потребует проверки манифеста и digest; тест выше использовал пустой каталог и не доказывает её доступность. Нельзя считать HTTP disconnect гарантией остановки.

Параметр `keep_alive=0` вызывает выгрузку после завершения запроса. Версия Ollama и порядок pre-load/unload должны быть проверены: пустой запрос с этим значением не доказывает отдельную успешную загрузку с последующей проверкой состояния. Метод чистого load-only при сохранении этого параметра ещё не продемонстрирован. Первый тест не должен незаметно заменяться длинной генерацией или изменять профиль; короткий отдельный baseline разрешён только после подтверждённой загрузки и допуска.

## Экспериментальный допуск: что известно и чего не хватает

- **Измерено:** свободная RAM 4395.5 MiB в одном снимке, commit headroom 19325 MiB, свободная VRAM примерно 7442 MiB; тестовые лимиты и остановка собственных пустых процессов описаны выше.
- **Оценка:** размер файла Qwen 4B 2.6 GB и свободная VRAM не задают пиковую системную RAM/commit или CUDA расход. Численная величина пика модели не выводилась.
- **Неизвестно:** пиковая память и VRAM модели при 4096/32, вклад mapped files и GPU driver, пригодный резерв ОС, сохранение runner в job и latency остановки активной загрузки/CUDA, другие конкурентные GPU-задачи.

Job cap может ограничить экспериментальный commit, но без надёжного учёта отображённых файлов, GPU и драйвера он сам по себе не гарантирует свободную физическую RAM. Для допуска нужны свежие три замера, отсутствие конкурирующих запросов, температурные и telemetry gate, независимая проверка runner в job и достаточная физическая RAM/VRAM для явно заданного commit cap **плюс** обоснованный резерв ОС и верхняя граница иных неучтённых ресурсов. Если эта граница не доказана, нужен больший подтверждённый запас, например профилирование на машине с существенно большей RAM, с сохранением того же GPU/backend и переносом результатов только после проверки сопоставимости. Нельзя считать этот пункт автоматическим разрешением на запуск на текущем ноутбуке; 8B production gate не изменён и не перенесён как 4B порог.

## Результат и следующий шаг

Загрузка, пиковые показатели 4B, размещение GPU, выгрузка, русский baseline, научные ответы и tool calling — **NOT RUN**. Подготовить отдельный изолированный model store, проверить hash и модельный runner в job на подходящей ресурсной площадке, уточнить совместимость load-only с `keep_alive=0`, задать доказуемые пределы и провести свежий трёхточечный допуск. Затем можно выполнить один контролируемый запуск с мониторингом и отдельно оценить короткие ответы и инструменты. Модель и проект **NOT READY**.
